**The implementation needs selective simplification, not a wholesale replacement of records with dictionaries or functions.** Its records contain no custom methods; computation and validation already use standalone functions. The larger problems are duplicated information, repeated structural validation, outdated normalized-value contracts, and representations selected before their scientific consumers exist.

I inspected the current source and corresponding tests. This was static analysis: **no files were modified and no tests were run**.

## 1. Module-wide assessment

The future workflow needs three different kinds of information:

| Information | Appropriate representation |
|---|---|
| Fixed dataset, partition, model, and evaluation inputs | Explicit references and small records with clear ownership |
| Predictions, reports, and failure provenance | Direct scientific payloads with unambiguous sample/class associations |
| Execution, stop, delivery, persistence, and acceptance observations | Separate operational facts owned by their respective components |

Scientific functions should consume the first category and produce the second. The third belongs to the surrounding workflow. Flattening should shorten access paths and remove competing copies of facts, while preserving these boundaries.

Several existing choices are justified:

- `UnitKey` expresses a useful, hashable parent/model identity.
- `PartitionReference` binds a dataset to its realized partition.
- Separate configuration and parent records preserve prospective-edit and resume semantics.
- `TraceContext` is useful across scientific and operational failures.
- Report status cannot reliably be inferred from payload presence.
- Stop request, observed stop, scientific completion, and result acceptance must remain distinct.
- Generic type parameters provide static typing; they do not themselves introduce runtime state.

The implemented `state.py` currently contains only `ExecutionStatus`, `ParentProgress`, `AttemptStatus`, and `StopStatus`. Most planned operational records and compatibility functions are **not implemented**. Their absence is unfinished Phase 1 work, not evidence of excessive implementation.

| Issue | Evidence | Assessment |
|---|---|---|
| Standardized labels still accept integers, floats, and booleans | `identity.py:12,101`; corresponding acceptance tests | Direct mismatch with updated policy |

The performance concerns above follow from the call structure; I have not measured their runtime cost.

### 3.1 `identity.py`: correct standardized labels

**Location:** [identity.py, lines 10–15 and 101–131](E:/swectral_new/cocoonet/src/cocoonet/_contracts/identity.py:10).

**Intention:** Apply the already-established text-label contract without adding a normalization framework.

**Proposed revision:**

- Remove the finite-float label branch and its now-unused `isfinite` import.
- Preserve the identifier types and `UnitKey`.
- Perform no integer-to-text conversion here: that remains input standardization.
- Do not combine this with the separate target-schema decision.

The corresponding function would be:

```python
type ScalarLabel = str


def validate_label(value: ScalarLabel, *, field: str) -> None:
    """Validate a standardized text label without conversion.

    Parameters
    ----------
    value : str
        Standardized sample, model, group, or class label.
    field : str
        Field path included in validation errors.

    Raises
    ------
    TypeError

    Notes

    # Require the standardized representation; never repair an internal label.
    validate_declared_types(value, expected_type=str, field=field)
```

Retaining the existing type-checking call in this first correction avoids combining semantic migration with validation-engine replacement.

**Associated changes:** Update dependent docstrings that discuss finite float labels or Python scalar-equality collisions. Update numeric-label acceptance fixtures throughout the contract tests.

**Unit review:** **Policy correction.** Necessary and bounded. Narrowing the shared alias and updating its directly affected fixtures is a coherent consistency revision. No new helper or model-label domain is needed.

> The supplied schedule’s targets must agree with the parent’s task kind and, for classification, its authoritative class vocabulary. This checks metadata associations without loading source features.

**Functional-block comments:**

```python

# Bind target interpretation to the parent's explicit evaluation task.

# Check classification targets against the authoritative class vocabulary.
```

**Unit review:** **Roadmap-first for the exact target representation and validation boundary.** The defect is established, but choosing a floating type silently would exceed the settled contract. Resolve that narrow decision before drafting the coordinated source revision.

### 3.6 `prediction.py`: preserve alignment, review storage, fix diagnostics

**Location:** [Prediction records](E:/swectral_new/cocoonet/src/cocoonet/_contracts/prediction.py:19), [regression validation](E:/swectral_new/cocoonet/src/cocoonet/_contracts/prediction.py:121), and [classification validation](E:/swectral_new/cocoonet/src/cocoonet/_contracts/prediction.py:411).

A sparse representation could associate failures with:


- one unavailable probability with an available predicted label;
- a shared fold failure;
- later successful folds;

```python
# Report the first mismatch with bounded context, not the complete dataset.
```

### 3.8 `_type_validation.py`: migrate away from the general engine

**Location:** [Imports and general machinery](E:/swectral_new/cocoonet/src/cocoonet/_type_validation.py:1), [recursive structured validation](E:/swectral_new/cocoonet/src/cocoonet/_type_validation.py:980), and [public utility functions](E:/swectral_new/cocoonet/src/cocoonet/_type_validation.py:1377).

**Intention:** Make primitive contract checks independent of unrelated scientific frameworks and remove validation machinery without a current consumer.

Current evidence:

- All implemented contract modules use `validate_declared_types`.
- A schedule is recursively traversed before individual samples and sources are validated again.
- Failure collections recursively traverse records/context before invoking their validators.
- Result prediction collections are traversed before per-batch validation.
- The decorator and dtype helper interfaces have no callers elsewhere in production source.

**Proposed migration:**

1. Specify a small, standard-library-only type-checking and bounded-diagnostic boundary.
2. Migrate validators in dependency order. Each checks its own fields and delegates nested records once.
3. Keep complete checks at independently loaded/produced boundaries. Do not add `skip_validation=True`, persistent “validated” flags, or caches tied to mutable objects.
4. Remove the annotation interpreter, decorator, and unused dtype interfaces only after their production consumers have been migrated and the approved scope explicitly covers removal.
5. Implement framework-specific validation later where an actual array/table/tensor consumer requires it.

Do not remove scientific package dependencies from project configuration as part of this proposal; their module-wide role is a separate decision.

**Associated helper docstring requirements:**

> Check an explicitly supplied runtime type requirement without interpreting typing annotations or traversing nested records. Reject booleans where integer or floating contracts exclude them. Report field, expected type, observed type, and a bounded value preview without coercion.

For diagnostic support:

> Generate bounded diagnostic context without scanning complete containers, moving tensors, or replacing the original validation error when preview generation fails.

**Functional-block comments:**

```python
# Check this boundary's immediate fields before accessing their values.

# Delegate each nested record once to its owning validator.

# Keep diagnostic work bounded independently of the supplied payload size.
```

**Unit review:** **Roadmap-first migration, not one replacement unit.** Reimplementing a smaller annotation interpreter would retain the underlying over-engineering risk. Exact new helper signatures and removals must be enumerated before implementation approval.

## 5. Recommended revision order

1. Correct standardized labels and their directly affected documentation/tests.
2. Resolve the target representation and task-context validation boundary.
3. Record the selected source, parent, report, and attempt-result schemas in Phase 1.
4. Implement those bounded schema migrations with their corresponding validators/tests.
5. Derive the attempt outcome through one approved pure function.
6. Migrate validation support without weakening independent boundaries.
7. Select a prediction-container change only after its ownership and scientific-consumer examples justify it.

The highest-value changes are **correcting standardized values, removing duplicated identity, deriving the attempt summary, and narrowing validation responsibilities**. Replacing every record or tuple would add migration work without an established module-wide benefit.
