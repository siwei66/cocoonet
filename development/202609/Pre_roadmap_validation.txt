````text
MY ADVICE:

Please update both root `AGENTS.md` and `docs/architecture.md` to incorporate the following architectural clarification before creating the implementation roadmap.

The goal is to define the **user-facing lifecycle and architectural contracts**, without prematurely fixing every Python method signature or implementation detail.

## 1. Core object model

CocooNet has a reusable root-side **computation instance**.

The computation instance is **not** itself a parent task.

Each call to `start()` creates a new parent evaluation task from the computation's current configuration:

```text
Reusable computation
    │
    ├── one active dataset
    ├── zero or more models
    ├── zero or more workers
    ├── evaluation/split configuration
    │
    └── start()
            ↓
       Parent task
            ├── unit tasks
            ├── execution attempts
            └── results/reports
```

The same computation instance may later be modified and reused to create another parent task.

This distinction must be explicit because it affects identity, persistence, recovery, worker reuse, dataset reuse, and roadmap ordering.

## 2. Intended user workflow

The normal workflow is:

```text
1. Create computation instance with evaluation configuration.
2. Add the dataset at the root.
3. Add model(s).
4. Add worker(s):
   - root-local worker,
   - online worker(s),
   - or both.
5. Optionally prepare/inspect the data split.
6. Call start().
7. Root validates prerequisites and prepares a new parent task.
8. Evaluation runs.
9. After completion, failure settlement, or completed break/cancellation,
   the computation becomes configurable again.
10. User may modify/copy/reuse it and start another parent task.
```

Do not require this exact method-call order unless a real dependency requires it.

Incomplete configuration is valid before `start()`.

For example, a computation may temporarily have a dataset and models but no worker.

## 3. Configuration is locked during execution

While a parent task is running, execution-defining configuration must not be modified.

Conceptually:

```text
CONFIGURABLE
    ↓ start()
RUNNING / LOCKED
    ↓ completion or fully settled break
CONFIGURABLE
```

Therefore a later operation such as removing a model applies only after the active parent task has settled; it must not retroactively alter the running parent task.

The exact locking mechanism is an implementation detail.

## 4. Reuse and copying

Users should be able to reuse an established computation efficiently, for example:

- same dataset, different model set;
- different workers;
- different permissible evaluation configuration;
- replaced dataset;
- copied computation configuration.

Copying should primarily mean copying the **computation configuration**, not cloning live runtime state such as:

- active worker processes;
- online connections;
- running attempts;
- accepted results;
- heartbeat/reconnect state.

If exact copy semantics remain unresolved, report them rather than inventing them.

## 5. Dataset contract

A computation has **exactly one active dataset**.

`dataset_id` provides stable dataset identity for persistence/reuse, especially on workers.

A dataset may persist across multiple parent tasks so that workers do not need to receive the same dataset again unnecessarily.

Example:

```text
Parent Task 1:
    dataset D
    models A/B

Parent Task 2:
    same dataset D
    models C/D
```

A worker that still retains the valid representation of dataset D should be able to reuse it according to the persistence contract.

Changing models alone must not inherently invalidate the dataset or valid realized partitions.

Replacing the dataset does invalidate partitions associated with the previous dataset.

Changing split-defining configuration also invalidates the corresponding realized partitions.

## 6. Dataset configuration versus persistence

Keep these concepts separate:

```text
Remove/replace active dataset
    → changes computation configuration.

Clear persisted dataset
    → removes retained root/worker copies used for reuse.
```

Do not make `rm_dataset()` implicitly mean “delete every persisted copy everywhere.”

The user should have explicit persistence-management capability, including manual clearing.

Exact API naming can be deferred.

## 7. Dataset representation

The canonical dataset abstraction is sample-oriented and tabular.

CocooNet must distinguish:

```text
internal sample_id
```

from:

```text
user-facing sample_label
```

The user does not need to provide CocooNet's internal `sample_id`.

For sklearn-style data:

```text
sample_label | y | X0 | X1 | ... | Xn
```

For inline PyTorch/tensor data:

```text
sample_label | y | shape | X0 | X1 | ... | Xn
```

with deterministic reconstruction and:

```text
product(shape) == number of flattened X values
```

Do not silently pad, truncate, repair, or infer inconsistent tensor data.

For file-backed data:

```text
sample_label | y | X_file
```

`X_file` should represent a dataset-relative/logical source reference compatible with synchronization and worker-local resolution, not an assumption that the same root-machine absolute path exists on every worker.

Please report whether the architecture must decide now:

- whether inline and file-backed samples may coexist in one dataset;
- whether `shape` is always per-sample or may be dataset-global.

If these are implementation-local choices, classify them as safely deferred.

## 8. Data splitting

Data splitting belongs to the root/computation preparation lifecycle.

Workers must not independently generate their own partitions.

Realized training/testing memberships must be fixed and durably persisted before dependent evaluation begins, according to the existing partition-persistence contract.

The intended API includes a capability conceptually similar to:

```python

## 10. Root coordinator and worker roles

The root node always owns coordinator responsibilities.

It does **not** automatically act as a worker.

CocooNet supports:

```text
1. optional root-local worker
2. optional online worker(s)
```

These are independently optional.

Supported topologies are:

```text
local only
online only
local + online
```

The root-local worker must be explicitly configured.

## 11. No-worker behavior

Zero workers is a valid configuration state before execution.

It is not valid for `start()`.

If the user calls `start()` without any usable execution target, fail explicitly before model evaluation begins.

Do not:

- silently run models in the coordinator;
- automatically create/enable a local worker;
- create a fake network worker;
- wait indefinitely for a worker the user never configured.

This is a configuration/startup failure, not a baseline model-training failure.

Please also report whether the architecture already distinguishes:

```text
worker configured
```

from:

```text
worker currently runnable/available
```

For example, if the only configured online worker is disconnected when `start()` is called, should CocooNet fail immediately or allow the parent task to wait for that worker?

Do not assume the answer if it is not already defined.

## 12. Root-local worker design

When enabled, the root-local worker is a separate locally managed worker process.

The coordinator must dispatch to it through a direct local execution/control boundary.

Do not create WSS loopback or other fake network behavior merely to emulate an online worker.

The local worker does not require remote-only mechanisms such as:

- network authentication;
- heartbeat/reconnect;
- network dataset synchronization;
- network result delivery.

However, it must share the same applicable scientific/task contracts as online workers:

- parent configuration;
- dataset identity;
- persisted partitions;
- unit-task identity;
- execution-attempt identity;
- model execution rules;
- scientific calculations;
- failure semantics;
- result structures;
- duplicate-attempt handling;
- at-most-one-accepted-result behavior.

User model code must not run directly inside the root coordinator process.

The root-local worker is another **execution target**, not a separate evaluation implementation.

## 13. Networking is conditional

Networking is required only when online workers are used.

Local-only execution must work without initializing the online-worker network subsystem.

Conceptually:

```text
Local only:
    coordinator → local worker

Online only:
    coordinator → worker network → online workers

Mixed:
    coordinator → local worker
               → worker network → online workers
```

Distributed networking extends the execution system; it is not a prerequisite for evaluation.

## 14. Mixed scheduling

When both local and online workers exist, schedule across both using the same logical task system.

Duplicate attempts and accepted-result rules must remain topology-neutral.

For example:

```text
attempt A → local worker
attempt B → online worker
```

must still obey the same at-most-one-accepted-result contract.

Do not create separate local versus remote result-acceptance semantics.

## 15. Worker ownership/reuse

Please review whether workers are best understood as reusable root/computation resources used by successive parent tasks rather than objects owned exclusively by one parent task.

The clarified workflow suggests reuse across parent tasks, especially for:

- online connections;
- root-local worker processes;
- persisted datasets;
- resource accounting.

Do not invent exact process/connection lifetimes if they are not yet architecturally fixed.

Report remaining ambiguity.

## 16. CPU allocation

Each worker has a user-configurable CPU budget `n_cpu`, defaulting to that machine's available CPU count `N`.

Evaluation CPU capacity is:

```text
nCPU = max(1, min(n_cpu, N) - 1)
```

where:

```text
n_cpu = user-configured CPU budget
N     = available CPU count
nCPU  = resulting evaluation CPU capacity
```

`nCPU = 1` means serial evaluation.

Parallel evaluation occurs only when:

```text
nCPU > 1
```

Therefore both:

```text
n_cpu = 1
n_cpu = 2
```

intentionally produce serial evaluation.

This conservative behavior also applies to online workers.

Do not state that the formula guarantees one physical CPU is always unused; the minimum evaluation capacity of one takes precedence.

Coordinator/worker-control responsiveness remains an independent requirement.

## 17. Existing scientific failure contracts remain unchanged

Do not change the existing failure-isolation rules.

Keep configuration/startup failures distinct from:

- baseline model-training failure;
- report failure;
- shared-intermediate failure;
- influence-analysis sample failure;
- worker/infrastructure failure.

In particular, “no worker available” occurs before scientific model evaluation and must not be reported as a model-training failure.
````

Some distinctions are particularly important to preserve during planning:

- Fixed partitions do not promise deterministic model outputs.
- Terminal baseline failure ends the unit evaluation, not the parent task or worker process.
- A failure-only file remains an acceptable complete outcome.
- Delivery exhaustion can leave a logical task unfinished while its worker returns to ordinary task handling. The documents expressly prohibit automatic recomputation, promotion of another result, and silent retry-budget resets.
- Cooperative duplicate cancellation and mandatory cleanup before another user apply to different lifecycle situations; cleanup cannot be declared successful while prior execution can recreate state.

**Conclusion: READY WITH NON-BLOCKING CLEANUP.** The documents can serve as the frozen architectural basis for roadmap generation. Preserve their established contracts, clean up the identified wording, and settle deferred mechanisms immediately before the implementation work that depends on them.
