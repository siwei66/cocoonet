# AGENT.md

## Project Overview

Cocoonet is a distributed engine for large-scale evaluation of machine learning models across decoupled, heterogeneous nodes. Designed for scientific computing, it provides an infrastructure where compute-heavy evaluation routines (e.g., cross-validation, leave-one-out, or sample influence evaluations) execute independently on remote worker nodes with minimal data transfer. The primary dataset is synchronized to nodes once initially, while the central coordinator dispatches only model definitions or hyperparameter configurations and asynchronously ingests returned evaluation reports.

**Model Scope & Task Flow:**
The framework explicitly accepts `scikit-learn-like models` (implementing standard `fit` and `predict` interfaces) as well as `PyTorch models`.
The root (user) node dispatches model definitions, hyperparameters, and execution directives as discrete tasks to the worker network.
Workers evaluate the models against a once-synchronized primary dataset using user-specified data splitting strategies like `k-fold`, `grouped k-fold`, `Leave-One-Out (LOO)`, `Leave-One-Group-Out (LOGO)`, and standard `train-test splits`.
Finally, the workers return the serialized evaluation reports (predictions, metrics) back to the root (user) node.

The software requires the highest level of auditability, transparency, and reproducibility for scientific research.

## Architecture Principles

* Independent & Decoupled Execution:
All worker nodes operate asynchronously, embarrassingly parallel, and without inter-node communication or shared distributed state. Task execution must remain completely independent.
* Minimal Wire Overhead:
The dataset is distributed once initially. The coordinator transfers only models or model recipes, and execution directives over the network. Workers return serialized evaluation reports (predictions, scalar metrics).
* Strict Task Idempotency:
Worker jobs must be idempotent. Retries, reassignments, or duplicate executions caused by timeouts, network resets, or speculative execution must not corrupt coordinator state or produce duplicated entries.
* Zero-Deserialization Streaming:
The central root node must ingest incoming serialized report payloads (`.dill`) directly to disk asynchronously. Never deserialize incoming reports within the active network event loop.
* Scientific Reproducibility & Auditability:
All data splits, random generators, and execution environments must be explicitly seeded, logged, and deterministic where mathematically possible. Every state change and dispatch decision must be traceable through structured logging.

## Technical Stack

* Language: Python 3.10+
* Asynchronous Networking & I/O: `asyncio`, `aiofiles`, standard HTTP/WebSocket protocols (pull-based architecture over port 443)
* Serialization: `dill` / `pickle` for model definitions and raw metric payload streaming
* Formatting & Linting: `black`, `ruff`
* Static Type Checking: `mypy` (strict mode)
* Testing: `pytest`, `pytest-asyncio`

## Code Quality Standards

* NumPy-Style Docstrings:
Every class, function, and class method must include a complete NumPy-style docstring specifying:
* A clear summary of the component's intent and responsibility.
* Explicit `Parameters` entries with types and descriptions.
* Explicit `Returns` or `Yields` entries with expected outputs.
* `Raises` sections for all explicitly handled exceptions.
* Realistic code examples demonstrating usage where non-trivial.


* Mandatory Logic Comments:
Never write major algorithmic logic or decision branches without clear, inline explanatory comments. Every non-trivial step must explain the *rationale* behind the implementation, not merely describe the syntax.
* Structural Length & Complexity Constraints:
* Line Length: Maximum of 120 characters per line across all source and test files.
* Function Length: Functions and methods must remain medium in length (typically 20–100 lines). If a routine exceeds this, break it into private single-responsibility helper functions.
* File Length: Source files must maintain medium length (typically under 300–500 lines) with sharp domain boundaries.


* Static Typing & Linter Compliance:
All code must pass `mypy`, `black`, and `ruff` without warnings or suppressions prior to being accepted.
