# 5. Important tips for planning and implementation with Codex

For this particular project, I recommend using Codex in **architecture-sized increments rather than file-sized increments**.

### 1. Make `AGENTS.md` the rules, not the specification database

Keep stable operating constraints in `AGENTS.md`:

* where Codex should look;
* what it must never violate;
* commands it must run;
* definition of done;
* compatibility/security rules.

Put detailed designs elsewhere:

```text
AGENTS.md
architecture.md
roadmap.md
docs/
├── protocol/
│   ├── task-protocol.md
│   ├── report-protocol.md
│   └── versioning.md
├── design/
│   ├── coordinator.md
│   ├── worker.md
│   ├── dataset-sync.md
│   └── artifact-storage.md
├── reproducibility.md
└── testing.md
```

OpenAI's own guidance now specifically describes a pattern in which `AGENTS.md` serves as the map and the deeper repository knowledge lives in structured documentation. ([OpenAI][2])

### 2. Design your protocol before implementing networking

For Cocoonet, I would not start by asking Codex to “implement the coordinator” or “implement WebSockets.”

First define:

```text
DatasetIdentity
WorkerIdentity

TaskId
AttemptId
TaskDescriptor
TaskStatus
TaskFailure

ReportDescriptor
ArtifactDescriptor

ProtocolVersion
SchemaVersion
```

Then define their invariants.

Networking becomes substantially easier once these contracts are stable.

### 3. Separate logical task identity from execution attempt identity

This is probably the most important distributed-systems design decision in the project.

For example:

```text
logical task T123
    attempt A1 -> worker W1 -> timeout
    attempt A2 -> worker W2 -> succeeds
    attempt A1 -> late success
```

The coordinator needs deterministic rules for what happens to that late success.

Do not defer this decision until retry logic is implemented.

### 4. Build a local reference execution path before distributed execution

Before remote workers are involved, implement a single-process reference path that can perform:

```text
dataset
  ↓
split specification
  ↓
model
  ↓
fit/evaluate
  ↓
EvaluationReport
```

Then distributed execution becomes a mechanism for executing the same semantic task elsewhere.

This gives you an excellent oracle for integration testing:

```text
local evaluation ≈ distributed evaluation
```

for deterministic models and workloads.

### 5. Implement vertical slices

A good Codex task should be something like:

> Implement TaskId parsing and validation according to `docs/protocol/task-protocol.md`. Add focused unit tests. Do not modify the network layer.

Then:

> Implement TaskDescriptor validation using the existing TaskId implementation. Add corresponding tests.

Then:

> Implement coordinator persistence for accepted TaskDescriptors.

This produces far more reliable output than:

> Build the coordinator.

### 6. Give Codex explicit acceptance criteria

For every task, specify:

```text
Goal
In scope
Out of scope
Relevant documentation
Invariants
Expected files
Tests required
Validation commands
Compatibility constraints
```

The “out of scope” section is particularly valuable for this project because otherwise an agent may opportunistically redesign protocol or abstractions while solving a small problem.

### 7. Ask Codex to inspect before changing

For implementation prompts, make the first requirement something like:

> Inspect the applicable AGENTS.md, architecture documentation, implementation, tests, and callers before editing. Do not change code until the current contract and affected dependencies have been identified.

Codex supports repository-scoped `AGENTS.md` instructions, and more deeply nested `AGENTS.md` files can apply more specific guidance to subtrees. ([OpenAI][4])

That means later you could use:

```text
AGENTS.md
src/
├── coordinator/
│   └── AGENTS.md
├── worker/
│   └── AGENTS.md
└── protocol/
    └── AGENTS.md
```

Only do this where subdirectory rules genuinely differ. Otherwise a single root file is easier to maintain.

### 8. Make test commands deterministic and explicit

Once your package tooling is chosen, put exact commands in `AGENTS.md`, for example conceptually:

```text
focused unit test
type checking
linting
format check
full test suite
integration tests
```

Use the **actual commands from your repository**, not generic ones.

Codex performs better when the repository has a configured development environment and reliable test setup, and OpenAI explicitly recommends putting navigation/testing guidance in `AGENTS.md`. ([OpenAI][3])

### 9. Test failure paths earlier than usual

For this architecture, I would prioritize failure tests almost immediately after the happy path:

```text
normal completion
duplicate completion
timeout + retry
late result
connection drop during result transfer
partial artifact
invalid checksum
worker dies
coordinator restarts
unsupported protocol version
corrupt serialized object
```

Distributed-system error behavior is substantially harder to retrofit after the happy-path protocol has solidified.

### 10. Avoid sleep-driven async tests

A test such as:

```python
await asyncio.sleep(0.1)
assert task.finished
```

is inherently fragile.

Prefer explicit signals such as:

```python
asyncio.Event
Queue
Future
mock transport completion
barrier-like helpers
```

Then the test verifies causality rather than machine speed.

### 11. Establish backpressure before load testing

Do not let Codex naturally evolve code into patterns such as:

```python
for request in requests:
    asyncio.create_task(process(request))
```

without a bounded lifecycle.

Define limits for:

* concurrent task execution;
* pending assignments;
* report uploads;
* artifact writes;
* memory buffering.

Otherwise a system that works beautifully with 10 tasks may collapse at 100,000.

### 12. Treat `pickle`/`dill` execution as a trust decision

Do not ask Codex simply to:

> deserialize the model and execute it.

First define whether models come from trusted users and whether workers are trusted execution environments.

Python explicitly warns against unpickling untrusted content because deserialization can execute arbitrary code. ([Python documentation][1])

For model objects, that security question is inseparable from the architecture.

### 13. Keep scientific metadata separate from operational logs

Structured logs are valuable, but they should not be the only place from which an experiment can be reconstructed.

I recommend having a first-class object conceptually similar to:

```text
EvaluationManifest
├── task identity
├── dataset fingerprint
├── model/config fingerprint
├── split definition
├── seeds
├── runtime versions
├── worker metadata
├── artifact hashes
└── status
```

Persist that next to or inside the evaluation report.

### 14. Let Codex change docs and implementation together when the design is already determined

I would avoid the current rule requiring:

> update docs → commit → new task → implement.

That creates process overhead without necessarily improving design quality.

A better distinction is:

**Unresolved design:** stop at the design decision.

**Resolved design but undocumented:** update documentation first, then implement it in the same coherent change if requested.

That still gives you documentation-first development without artificial session boundaries.

### 15. Have Codex report evidence, not merely completion

A useful final response from Codex should state:

```text
Changed
Why
Tests added/changed
Commands run
Results
Commands not run and why
Compatibility impact
Remaining risks
```

Avoid accepting only:

> Implemented successfully.

For a scientific/distributed system, evidence of validation is much more useful.

### 16. Preserve human review at protocol and security boundaries

Codex is well suited to implementation, testing, refactoring, and review, but OpenAI still recommends reviewing and validating agent-generated code before integration. ([OpenAI][3])

I would require especially careful human review for:

* task identity semantics;
* retry/state transitions;
* authentication;
* `pickle`/`dill` boundaries;
* artifact integrity;
* dataset fingerprinting;
* protocol versioning;
* cancellation handling;
* concurrency primitives;
* scientific split logic.

Those are the places where a locally reasonable implementation can create a subtle system-level error.
