The roadmap should prioritize:

* easiest foundations first;
* clear dependency order;
* small modular capabilities;
* stable data models and interfaces before dependent behavior;
* local/simple behavior before distributed behavior;
* persistence/state foundations before recovery/retry logic;
* minimal architectural churn during later implementation;
* milestones that can later be decomposed into very small reviewable change units.

## Roadmap Quality and Completeness Pass

Before finalizing `roadmap.md`, review the roadmap against both `AGENTS.md` and `architecture.md`.

Ensure that:

* every roadmap-relevant architectural component, responsibility, lifecycle, persistence requirement, execution boundary, and distributed-system capability is represented in an appropriate phase or explicitly deferred to a later phase;
* no roadmap-relevant architectural requirement is silently omitted;
* the roadmap ordering contains no hidden dependency on behavior, state, interfaces, persistence structures, or distributed capabilities that are only introduced in a later phase;
* circular or bidirectional implementation dependencies are identified and, where the existing architecture permits it, reduced by introducing foundational interfaces, data models, or state structures before the capabilities that depend on them;
* each phase is internally coherent and does not combine unrelated capabilities merely to reduce the number of phases;
* the expected architectural state at the end of each phase is clear enough that the next phase can begin without redesigning completed work;
* genuine architecture gaps that affect roadmap ordering are distinguished from implementation details that can safely be decided later;
* capabilities intentionally deferred from an earlier phase are actually introduced in an appropriate later phase;
* recovery, retry, reconnection, failure handling, cleanup, and other advanced lifecycle behavior are introduced only after the normal-path state, persistence, communication, and lifecycle foundations they depend on are stable;
* phases can later be decomposed into small, locally reviewable implementation changes without requiring simultaneous changes across many unrelated subsystems.
