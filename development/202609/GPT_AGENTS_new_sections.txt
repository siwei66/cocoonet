# 3. Other needed sections for `AGENTS.md`

I recommend adding the following sections. I have intentionally kept each one in a **separate quoted text block** so you can decide individually whether to insert it.

## A. Repository Sources of Truth

> ## Repository Sources of Truth
>
> Agents must distinguish normative project documents from descriptive or historical documents.
>
> Unless more-specific repository documentation states otherwise, use the following precedence:
>
> 1. Explicit user requirements for the current task.
> 2. Applicable `AGENTS.md` instructions.
> 3. `architecture.md` for architectural invariants and component boundaries.
> 4. Protocol/schema specifications for wire and persistence contracts.
> 5. `roadmap.md` for planned scope and sequencing.
> 6. Tests for currently enforced behavior.
> 7. Implementation code for current mechanics.
> 8. Comments, examples, and historical notes.
>
> If two normative sources conflict, do not silently choose one based on implementation convenience. Identify the conflict and resolve the governing contract before introducing new behavior.
>
> Tests that contradict an explicitly documented architecture may indicate either a regression or stale documentation; investigate rather than automatically treating either source as authoritative.

### Why this section is needed

Your current file has a documentation-first rule referencing `architecture.md` and `roadmap.md`, but it does not define what happens when documentation, tests, and code disagree.

That ambiguity becomes particularly problematic for Codex because it can see several apparently authoritative sources at once. Giving it an explicit hierarchy materially reduces accidental “fixes” that actually violate the intended architecture.

OpenAI itself recommends using `AGENTS.md` as persistent repository guidance and, for larger agent-oriented repositories, treating it more like a map into structured documentation than an encyclopedia containing every detail. ([OpenAI][2])

## B. Security and Trust Boundaries

> ## Security and Trust Boundaries
>
> Cocoonet executes and transports Python model objects and therefore must explicitly distinguish trusted code from untrusted data.
>
> ### Serialized Python Objects
>
> `pickle`, `dill`, or equivalent Python-object serialization must never be treated as a safe untrusted-input format.
>
> Do not deserialize a model, task payload, result artifact, or other Python object unless its source is within the explicitly documented trust boundary.
>
> ### Authentication and Integrity
>
> Network protocol design must provide a way to establish:
>
> * worker/coordinator identity;
> * authorization to submit or execute work;
> * integrity of task and report payloads; and
> * correspondence between an artifact and its expected task.
>
> Do not assume that transport encryption alone establishes application-level trust.
>
> ### Secrets
>
> Never:
>
> * commit credentials, access tokens, private keys, or passwords;
> * include secrets in task/report payloads unless explicitly required;
> * write secrets to structured logs;
> * expose secrets in exception messages; or
> * include real credentials in tests or examples.
>
> ### Resource Isolation
>
> Model execution must be considered arbitrary user-code execution unless the project defines a narrower trusted execution model.
>
> New functionality must not implicitly weaken process, filesystem, environment, network, or resource isolation assumptions.
>
> ### Input and Artifact Validation
>
> Validate protocol metadata, identifiers, declared lengths, checksums, supported protocol versions, and resource limits before expensive processing or deserialization where practical.

### Why this section is needed

For this project, this is not optional hardening. A distributed ML system carrying pickled/dilled model objects creates a direct code-execution trust boundary.

Python's documentation states that unpickling untrusted or tampered data can execute arbitrary code. ([Python documentation][1])

Your architecture therefore needs a conscious answer to questions such as:

* Is every worker fully trusted?
* Is the root fully trusted by workers?
* Can users submit arbitrary models?
* Can worker-produced `.dill` reports ever be untrusted?
* How are workers authenticated?
* How is artifact tampering detected?

`AGENTS.md` does not need to answer all of these, but it should prevent Codex from accidentally implementing a design that assumes they do not matter.

## C. Task Identity, State, and Idempotency Contract

> ## Task Identity, State, and Idempotency Contract
>
> Every distributed task must have a stable logical identity that is independent of a particular network connection, worker assignment, retry attempt, or process lifetime.
>
> Unless the architecture explicitly defines otherwise:
>
> * retries preserve logical task identity;
> * execution attempts have distinct attempt identities;
> * duplicate successful reports for the same logical task must be detectable;
> * conflicting successful reports must not be silently accepted;
> * coordinator restart must not change the logical identity of existing tasks.
>
> Task lifecycle transitions must be explicit and validated.
>
> A typical lifecycle may distinguish states such as:
>
> * pending;
> * assigned;
> * running;
> * succeeded;
> * failed;
> * retryable;
> * cancelled; and
> * expired.
>
> Do not introduce a new state or state transition without updating the documented task lifecycle.
>
> State transitions must not depend solely on in-memory process state if coordinator restart/recovery is expected to preserve correctness.

### Why this section is needed

The current file says jobs must be idempotent, but idempotency is not an implementation property that emerges automatically. 

You need explicit semantics around:

**logical task → attempt → result**

Otherwise Codex could implement retry handling differently in multiple locations and create race conditions such as:

* task A times out;
* task A is reassigned;
* old worker finishes;
* new worker also finishes;
* both reports arrive;
* coordinator records two successes.

That is one of the central correctness problems of this architecture.

## D. Protocol and Artifact Contract

> ## Protocol and Artifact Contract
>
> Wire messages and persisted artifacts are compatibility-sensitive interfaces.
>
> Every protocol object should have an explicit schema or documented structural contract.
>
> Protocol-level metadata should include sufficient information to identify:
>
> * message or artifact type;
> * schema/protocol version;
> * logical task;
> * execution attempt where applicable;
> * dataset identity;
> * payload length or framing information where applicable; and
> * integrity information where required.
>
> Do not infer protocol semantics from Python class layout alone.
>
> ### Versioning
>
> Readers must reject unsupported protocol/schema versions explicitly rather than attempting best-effort interpretation.
>
> Compatible schema extensions should be designed intentionally.
>
> Breaking changes require:
>
> 1. an explicit version change;
> 2. documentation;
> 3. compatibility tests; and
> 4. migration or rejection behavior.
>
> ### Artifact Finalization
>
> Incoming artifacts must not appear as successfully committed artifacts until transfer and required integrity checks complete.
>
> Prefer staging followed by atomic finalization so readers never observe partially written successful artifacts.

### Why this section is needed

Your system relies on persistent serialized evaluation reports and remote task dispatch. That means your wire protocol and artifact layout effectively become APIs.

Without this section, Codex may naturally evolve Python classes while accidentally changing:

* serialized report structures;
* retry compatibility;
* persisted files;
* worker/coordinator compatibility.

This tends to become expensive to correct later.

## E. Reproducibility Manifest

> ## Reproducibility Manifest
>
> Every completed evaluation must be attributable to a reproducibility record or equivalent structured metadata.
>
> The record should contain, where applicable:
>
> * logical task ID;
> * execution attempt ID;
> * dataset ID and content fingerprint/version;
> * model/recipe identity;
> * complete evaluation parameters;
> * split strategy and split identity;
> * random seed values;
> * relevant package versions;
> * Python version;
> * platform/runtime metadata relevant to numerical behavior;
> * worker identity;
> * execution timestamps;
> * result artifact identities/checksums;
> * task status; and
> * error metadata for failed execution.
>
> For PyTorch or other frameworks where exact deterministic execution cannot be guaranteed, record relevant determinism settings and document known limitations.
>
> Reproducibility metadata must be machine-readable.
>
> Logs may supplement this metadata but must not be the sole source of information necessary to identify an evaluation.

### Why this section is needed

The current file correctly requires seeding and structured logging. 

For scientific research, however, a random seed alone is not sufficient. Reproducing an experiment often depends on:

`dataset + split + model/config + seed + environment + code/protocol version`

Making this an explicit data structure is much stronger than hoping all necessary facts can later be reconstructed from logs.

## F. Async and Concurrency Invariants

> ## Async and Concurrency Invariants
>
> Asynchronous code must preserve event-loop responsiveness and explicit ownership of mutable state.
>
> ### Event-Loop Safety
>
> Do not perform blocking filesystem, CPU-heavy, model-evaluation, compression, hashing of very large payloads, or deserialization work directly on the active event-loop path unless the operation is demonstrably bounded and negligible.
>
> ### Cancellation
>
> Cancellation is part of normal asynchronous control flow.
>
> Code must:
>
> * preserve cancellation rather than accidentally swallowing it;
> * perform required cleanup;
> * avoid leaving partially committed coordinator state; and
> * avoid representing cancellation as successful execution.
>
> ### Shared State
>
> Mutable coordinator state accessed by concurrent coroutines must have an explicit ownership or synchronization strategy.
>
> Do not add locks automatically. Prefer designs with clear state ownership and minimized shared mutation.
>
> ### Backpressure
>
> Network ingestion, task assignment, and artifact persistence must have bounded concurrency or another explicit backpressure mechanism.
>
> Do not create unbounded tasks, queues, buffers, or concurrent file transfers.

### Why this section is needed

Your architecture is explicitly based on `asyncio`, asynchronous workers, and asynchronous report ingestion. 

That makes event-loop blocking, cancellation, backpressure, and shared coordinator state first-class architecture concerns.

This section is likely to prevent more real bugs than generic style rules.

## G. Testing Strategy and Test Boundaries

> ## Testing Strategy
>
> Tests must be classified according to the behavior they verify.
>
> ### Unit Tests
>
> Unit tests should validate deterministic local behavior without requiring live external infrastructure.
>
> ### Protocol Tests
>
> Protocol tests should verify:
>
> * serialization/framing;
> * schema validation;
> * version handling;
> * malformed input handling; and
> * compatibility expectations.
>
> ### Async/Concurrency Tests
>
> Prefer explicit synchronization primitives over sleeps.
>
> Tests must not rely on arbitrary timing delays to establish ordering when deterministic coordination can be used.
>
> ### Distributed Failure Tests
>
> Important coordinator/worker behavior should test scenarios including:
>
> * duplicate task delivery;
> * duplicate result delivery;
> * worker disconnect;
> * timeout;
> * retry;
> * coordinator restart where supported;
> * partial artifact upload;
> * malformed report metadata; and
> * incompatible protocol versions.
>
> ### Scientific Correctness Tests
>
> Evaluation implementations should validate:
>
> * split membership;
> * absence of unintended data leakage;
> * deterministic split generation where applicable;
> * metric correctness; and
> * equivalence to a trusted local reference implementation where practical.
>
> ### Integration Tests
>
> Integration tests involving multiple coordinator/worker processes must remain isolated, reproducible, and suitable for automated execution.

### Why this section is needed

The existing file asks for granular unit tests, but Cocoonet's highest-risk defects are not ordinary single-function defects. They are likely to involve:

* retries,
* duplicated messages,
* partial transfers,
* async scheduling,
* split correctness,
* process boundaries.

A testing section should tell Codex which failure modes matter rather than only telling it to write tests incrementally.

## H. Validation Commands

> ## Validation Commands
>
> Repository commands listed here must reflect the actual project configuration. Do not invent commands that the repository does not support.
>
> Before completing a code change, run the narrowest applicable validation first and then the broader repository checks required for the changed scope.
>
> Once the repository exposes canonical commands, document them here for:
>
> * environment/bootstrap installation;
> * formatting;
> * linting;
> * static type checking;
> * unit tests;
> * integration tests;
> * complete test suite; and
> * documentation validation, if applicable.
>
> If a required command cannot be executed in the current environment:
>
> 1. state which command was not run;
> 2. state why;
> 3. report the validation that was performed instead; and
> 4. do not claim the unavailable check passed.
>
> Agents must never modify tests, lint configuration, typing configuration, or quality thresholds merely to make validation pass unless the requested task specifically concerns those configurations.

Once the repository structure is known, this should become one of the most concrete sections in the file.

## I. Definition of Done

> ## Definition of Done
>
> A code task is complete only when all applicable conditions are satisfied:
>
> * requested behavior is implemented;
> * implementation conforms to documented architecture;
> * affected tests are added or updated;
> * relevant tests pass;
> * formatting passes;
> * linting passes;
> * static type checking passes;
> * public or compatibility-sensitive behavior is documented;
> * no unrelated changes are included;
> * error and cancellation behavior has been considered;
> * reproducibility requirements are satisfied where applicable;
> * compatibility implications have been considered; and
> * any validation that could not be executed is reported explicitly.
>
> Passing tests alone does not establish completion if the implementation violates an architectural invariant.

### Why this section is needed

It gives Codex an explicit termination condition. Without one, coding agents can interpret “finished” as “the requested function exists,” even if type checking, protocol compatibility, documentation, or failure behavior remains unresolved.

# 4. Reasons for the new sections as a whole

The proposed additions fall into four categories.

**Repository governance:** “Sources of Truth,” “Validation Commands,” and “Definition of Done” tell Codex how to reason about the repository rather than simply how to format code.

**Distributed-systems correctness:** “Task Identity,” “Protocol and Artifact Contract,” and “Async and Concurrency Invariants” address the failure modes created specifically by your root/worker design. The existing document already establishes independent workers, asynchronous execution, minimal network transfer, and idempotency; the new sections make those principles operational. 

**Scientific correctness:** “Reproducibility Manifest” and the scientific portions of “Testing Strategy” make auditability enforceable as structured data and tests rather than only an aspiration.

**Security:** “Security and Trust Boundaries” is necessary because model serialization is not ordinary data serialization. Python explicitly states that unpickling untrusted data can lead to arbitrary code execution. ([Python documentation][1])

If you want to keep the root `AGENTS.md` short, I would prioritize these five additions:

1. **Repository Sources of Truth**
2. **Security and Trust Boundaries**
3. **Task Identity, State, and Idempotency Contract**
4. **Validation Commands**
5. **Definition of Done**

Then move the longer protocol, reproducibility, and testing specifications into dedicated files under `docs/` and link to them from `AGENTS.md`.

That approach is also consistent with OpenAI's current guidance from its own agent-oriented engineering experience: use `AGENTS.md` principally as a concise map and keep deeper system knowledge in structured repository documentation. ([OpenAI][2])
