| **Identifier scope and continuity across dataset representations** | An entire evaluation task operates on exactly one dataset. Within the active dataset, `sample_id` is used internally for computation and alignment, while the root-assigned sample `label` is used as the user-facing identifier in reports; no global or cross-dataset sample identity is required.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Configured-model identity**                                      | The root assigns each supplied model an arbitrary module-generated unique model\_id and associates it with a user-provided unique model label. Cocoonet uses model\_id internally for model references, task association, execution tracking, duplicate handling, and provenance. User-facing reports identify the model by its user-provided label; the internal model\_id may be retained in internal records for traceability. Cocoonet treats the supplied model or model-construction information as the authoritative executable model input. Recording and interpreting such metadata is outside the module's scope and remains the user's responsibility. The model input associated with a logical task is fixed for that task. | **Logical-task creation and configuration stability**              | A **model evaluation task** is the complete evaluation request submitted by the user and contains exactly one dataset, exactly one fixed task-wide evaluation method/configuration, and one or more models. The dataset is synchronized to the assigned worker environment before unit-task execution and is shared by all unit tasks; after this initial synchronization, unit-task transfers provide only the model and required model-specific information and neither resend nor separately identify the dataset. The evaluation method, including data-splitting, validation, and other task-wide evaluation settings, is defined once for the model evaluation task and cannot be overridden by individual models, so all models are evaluated under the same conditions and their results remain directly comparable. A **unit task** is the evaluation of exactly one model within its parent model evaluation task, with each model producing one unit task; because the parent already establishes the dataset and evaluation configuration, neither forms part of the unit-task identity, and the user-defined unique `model_label` is sufficient to distinguish unit tasks within that model evaluation task.
