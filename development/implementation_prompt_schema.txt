## Phase continuing prompt schema:

```text
Approved. Implement the proposed next unit directly. Do not introduce any change beyond the proposal.

---

Pass the dedicated pytest, mypy, black and ruff.
- Use venv `cocoonet` for all tests.
- Do not try to solve the pytest error automatically, report the pytest error with analysis and recommendation of solution instead.
- If the implementation does not pass mypy: 1. Verify the implementation first; 2. If the mypy error is limited to typing issue only, try to solve the typing issue without changing code logic, do not use cast or skip the error to solve it; 3. If the mypy error indicates any real type or variable mismatch risk, report instead of forcibly solving; 4. If you failed to solve it with one trial, give up and report the mypy error and its analysis in your final reply instead of trying to solve it again.
- Use black to solve black error found directly without changing the code or docstring content.
- Solve only the ruff error `I001` / `E501` / `F401` / `C420` automatically, report other ruff errors with analysis and recommendations of solution.

---

After finishing:
- Verify the compliance of current implementation to the development requirement of `AGENTS.md`, delivery a compliance report.
- Verify the over-engineering risk specifically i.e. verify the risk of too many layer of nesting, over-complicated logic, over-defensive for a light-weight python module and functional or coding redundancy in the context of `roadmap.md` and the phase roadmap. Considering whether a demand is really needed in the real implementation of current step and current phase, instead of view all roadmap demands as ground truth to follow. Deliver a over-engineering risk report.
- Then, propose a standard one-line git commit message for the changes with scope. If the changes have multiple associated scopes, propose one git commit message for each associated scope.
- At last, show me the progress of implementation of the current phase, and list the implemented units in the current phase in one table and list the units to be implemented in the current phase in another table.

---

Then, if there is no violation or major over-engineering risk or risk of unnecessary required functionalities, continue with the next unit.

Propose only. The proposal requirements are:

- Prepare only the next planned change unit.
- Show me the exact proposed implementation and corresponding tests, with a concise explanation of the change and any relevant implementation decision.
- Deliver the proposal in python code block with filename and the number of the line in the file to add the block.
- Read only the relevant `AGENTS.md` rules, the relevant `architecture.md` design, and the applicable section of the detailed phase roadmap of the current phase, and the directly affected code/tests.
- Do not perform a broad repository audit unless required by a detected dependency.
- Propose the exact change only.
- Do not modify files for next unit.
```

## For new detailed implementation-ready phase roadmap creation:

```text
Read the complete root `AGENTS.md`, `architecture.md`, and `roadmap.md` and the phase roadmaps of the previous phases in docs/roadmaps carefully.
Plan next phase only according to `roadmap.md`, the phase roadmaps of the previous phases, and the implementation of previous phases.

Create:
`docs/roadmaps/roadmap_phase_<k>.md`
(`<k>` is the index for the next phase to implement)

The phase roadmap must translate the next phase tasks into an implementation-ready plan while following all development and approval rules in `AGENTS.md`.

---

Define, where applicable:
- Phase goal, scope, and out-of-scope items;
- entry and completion criteria;
- relevant architecture contracts and invariants;
- required data models, fields, types, and invariants;
- public APIs and signatures;
- computation formulas and numerical behavior;
- planned classes, functions, and methods with concise responsibilities;
- directly corresponding tests;
- dependency-safe implementation order;
- validation requirements;
- decisions explicitly deferred to later phases.

---

Requirements:
- Plan implementation at function-/method-level granularity so later development can proceed mostly forward without unnecessary refactoring or jumping between subsystems.
- Resolve all ambiguities and contracts required to the current phase. If a required design decision for the current phase cannot be resolved from the development docs and the implementation of previous phases, do not guess: report it as a blocking ambiguity.
- Do not prematurely design later phases. Decisions needed only later should be explicitly deferred.
- Do not implement any source code or tests.
- Do not modify `AGENTS.md`, `architecture.md`, or `roadmap.md`. Modify only `docs/roadmaps/roadmap_phase_<k>.md`.

---

After creating the phase roadmap:
1. summarize and list its implementation order;
2. report any remaining blocking ambiguity;
3. report any inconsistency found among `AGENTS.md`, `architecture.md`, `roadmap.md`, the implemented phase scopes;
4. stop and wait for my approval before any implementation of the next phase begins.
```
