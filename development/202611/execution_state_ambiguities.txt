Ambiguities:

The model is substantially cleaner. It treats `execution_state.csv` as a current attempt-state table rather than a general persistence container for worker health, retry operations, diagnostics, and result metadata.

A root table could look like:

```csv
parent_id,worker_id,model_label,model_id,attempt_id,attempt_status
parent-1,worker-1,Random Forest,model-1,attempt-1,result_synchronized
parent-1,worker-2,Random Forest,model-1,attempt-2,aborted
parent-1,worker-1,Neural Network,model-2,attempt-3,running
```

From this, the root can derive:

```text
model-1 = finished
    because attempt-1 reached result_synchronized

model-2 = unfinished
    because no attempt reached result_synchronized

parent-1 = unfinished
    because at least one configured model remains unfinished
```

`model_label` is useful user-facing redundancy, while `model_id` remains the stable internal association. Duplicate attempts share the same model pair and are distinguished by `attempt_id`.

## What is now clearly unnecessary

Under this model, the earlier columns for parent status, worker availability, reception, persistence, operations, presence flags, and failure diagnostics are unnecessary.

The six approved fields are sufficient for current attempt progress:

```python
EXECUTION_STATE_COLUMNS = (
    "parent_id",
    "worker_id",
    "model_label",
    "model_id",
    "attempt_id",
    "attempt_status",
)
```

Detailed errors can remain in attempt-associated logs. A persisted result is identified through its model and attempt metadata, so a separate result-artifact identity is not required in this table.

## Ambiguities that remain

### 1. How many `not_allocated` attempts initially exist?

“States of all attempts are recorded with `not_allocated`” requires the attempt identities to exist before allocation.

For example:

```csv
parent-1,,Random Forest,model-1,attempt-1,not_allocated
```

This raises two questions:

- How many initial attempt IDs are created for each model?
- Is `worker_id` empty until a worker is selected?

Future duplicate attempts cannot all be known initially unless a fixed number is pre-created. The simplest interpretation is:

```text
Create one initial attempt per model as not_allocated.
Create an additional not_allocated attempt only when a retry or duplicate is requested.
```

Thus, “all attempts” means all attempts created so far, not every attempt that might ever be created.

### 2. Meaning of `allocated`

The ordering must be defined. Worker-specific data synchronization requires a worker to have already been selected, but the proposed statuses include synchronization before `allocated`.

The coherent ordering is:

```text
not_allocated
→ allocated
→ data_synchronizing
→ data_synchronized
→ model_synchronizing
→ model_synchronized
→ running
```

Here, `allocated` means:

```text
The attempt has a fixed worker assignment.
```

If `allocated` instead means that a compute slot is reserved only after synchronization, another state such as `worker_assigned` would be required. Adding that state would be less minimal, so allocation-before-synchronization is preferable.

### 3. Shared data synchronization

Data synchronization is specific to `(parent_id, worker_id)`, while the table stores it on each attempt.

Suppose two attempts use the same worker:

```text
attempt-1 → worker-1
attempt-2 → worker-1
```

If `attempt-1` synchronizes the parent data successfully, must `attempt-2` also pass through:

```text
data_synchronizing → data_synchronized
```

or may it reuse the worker’s existing data and transition directly from:

```text
allocated → model_synchronizing
```

I recommend allowing the latter. The state then describes the work actually performed for that attempt. Reused worker data does not require a fabricated synchronization transition.

### 4. Failure-state retry behavior

It must be established whether these states are terminal for one attempt:

```text
data_synchronizing_failed
model_synchronizing_failed
allocation_failed
attempt_failed
result_synchronization_failed
```

The simplest rule is:

```text
Every *_failed state is terminal for that attempt.
A retry creates a new attempt_id beginning at not_allocated.
```

This avoids backward transitions such as:

```text
result_synchronization_failed → result_synchronizing
```

and produces an unambiguous attempt history.

If result transfer should be retried under the same attempt ID, then `result_synchronization_failed` cannot be terminal and permitted retry transitions must be specified.

### 5. `attempt_finished_with_error` versus `attempt_failed`

These require exact definitions:

```text
attempt_finished_with_error
    A complete valid result was produced, but it contains recorded scientific
    errors or unavailable results. It proceeds to result synchronization.

attempt_failed
    No complete valid result was produced. It cannot proceed to result
    synchronization.
```

Without this distinction, users and recovery code cannot know whether a result should still be synchronized.

### 6. Meaning of `result_synchronized`

Under the approved interpretation, it must mean all of the following:

```text
The root received the complete result.
The root successfully persisted it.
The persisted result is authoritative for that model unit.
```

No separate receipt, persistence, or acceptance state is then needed.

For duplicates:

```text
attempt-1 = result_synchronized
attempt-2 = aborted
```

`attempt-1` determines completion for the model unit.

### 7. Worker and root disagreement after an acknowledgement loss

If the root persists a result but its acknowledgement does not reach the worker:

```text
Root record:
    result_synchronized

Worker record:
    result_synchronizing
```

The root must be authoritative. On reconnection, the worker accepts the root’s status and does not retransmit or replace the persisted result.

### 8. Crash behavior

“Crash will not have any record” is workable if it means no new failure status is fabricated.

For example, if a worker crashes while running, the root may retain:

```text
attempt_status = running
```

The root then observes:

```text
no synchronized result
no active worker connection
```

and creates another attempt. It must not rewrite the old attempt as `attempt_failed` unless an actual failure status was received.

This means the table contains the last durably observed state, not necessarily the worker’s unknowable final physical state.

### 9. `stopped` versus `aborted`

The distinction is clear:

```text
stopped
    Work ended because the parent was interrupted or the worker lost its
    parent connection.

aborted
    Work became unnecessary because another duplicate attempt was accepted.
```

One remaining behavioral distinction is resumption:

- A `stopped` attempt may be resumed or replaced after the parent resumes or reconnects.
- An `aborted` attempt is terminal and must never resume or contribute a late result.

### 10. Physical CSV format

Previous discussion required exactly two physical columns:

```csv
field,value
```

The new list calls the six names “columns.” It must be clarified whether they are:

1. Actual wide CSV columns:

```csv
parent_id,worker_id,model_label,model_id,attempt_id,attempt_status
```

or:

2. Logical items written as repeated fixed `field,value` blocks:

```csv
field,value
parent_id,parent-1
worker_id,worker-1
model_label,Random Forest
model_id,model-1
attempt_id,attempt-1
attempt_status,running
```

The data model works either way, but the physical encoding and decoder are different. Based on the earlier approved metadata persistence rule, the second interpretation appears intended.

### 2. Meaning of `aborted` after worker loss

Initially, `aborted` was defined as:



Therefore, `aborted` currently has two causes:


### 3. Whether `aborted` proves worker-side deletion

You specified that an aborted attempt removes all worker-side persistence. That cannot always be guaranteed when the worker has crashed or remains unreachable.

```text

It is not proof of physical deletion when the worker is unreachable.
Deletion must occur when the worker reconnects or before that worker is reused
or released.
```

If `aborted` must prove confirmed deletion, the root cannot mark a crashed worker’s attempt as aborted until cleanup is acknowledged. Those two requirements cannot both hold simultaneously.

### 4. Final state after result-reconnection exhaustion

You specified both:

- `result_synchronization_failed` is terminal.
- After connection retries are exhausted, the worker stops the attempt.

It remains unclear whether retry exhaustion produces:

```text

```

```text

```

Recommended distinction:

```text
result_synchronization_failed:
    Result delivery or root persistence failed after its permitted retries,
    while the parent relationship still existed.

stopped:
    The parent connection could not be re-established within its connection
    limit, or the parent explicitly interrupted execution.
```

Transient synchronization failures do not change the status from `result_synchronizing`; only final exhaustion changes it.

### 5. Root and worker file scope

The root scope is clear: its file contains every attempt created for the parent.

The worker scope is not yet explicit. Recommended interpretation:

```text
Root execution_state.csv:
    Contains every attempt for every model in the parent, including

    Contains only attempts assigned to that worker.
```

The root mirrors received worker status but remains authoritative for `aborted` and `result_synchronized`.

### 6. Durable result selection

With duplicate attempts, only one may enter root result synchronization. The model currently has no separate selected-attempt field, so `result_synchronizing` must serve as durable selection.

The required invariant should therefore be:

```text
For one parent/model pair, at most one attempt may be result_synchronizing or
result_synchronized.

Once one attempt enters result_synchronizing, no other duplicate may enter
result synchronization.

After it reaches result_synchronized, all remaining attempts become aborted.
```

It is unclear whether a terminal `result_synchronization_failed` attempt permits another existing duplicate to be selected. Your explicit user-retry rule could instead require creation of a new attempt. This must be stated because it changes duplicate arbitration.

### 7. Retry after `result_synchronization_failed`

You allow the user to retry a failed attempt by creating another attempt. For result synchronization failure, two different actions are possible:

- Create a new attempt and recompute the model.
- Reuse the already completed worker result and retry only synchronization.

Because the original attempt already completed its scientific work, recomputation is normally unnecessary.

Recommended interpretation:

```text

After result_synchronization_failed:
    That attempt is terminal and is never resumed.
```

This follows your rule that every failure status is terminal, but it should be explicitly accepted because it may repeat expensive scientific computation.

```text
Initial attempts follow the fixed model order in execution_configuration.csv.
Later duplicate and retry attempts are appended in creation order.
Atomic replacement preserves that order.
```

Rows should not be sorted by worker or current status because those values can change.
