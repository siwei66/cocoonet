## Issue 5 — Root lifecycle and shared resume/reconciliation

### Analysis

The architecture can settle lifecycle behavior independently of the eventual public method name:

- the root work directory must be bound before dataset preparation;
- execution entry cannot silently select or replace it;
- explicit interruption and unexpected root termination use one persisted-state reconciliation procedure;
- a post-crash user recreates the root-side instance against existing storage;
- a same-process interruption can reuse the existing instance;
- explicit interruption remains a distinct recorded event because it unlocks prospective edits and initiates cooperative stopping.

The public name remains blocked: current `AGENTS.md` requires `start()`, while the advice says no `start` method is planned. Architecture cannot silently replace that governing requirement.

# MY ADVICE: propose revision of removal of exact method name in `AGENTS.md` and allow later planning of method names first.

### Exact revision

Under Section 2.3, after the directory-preparation table and overwrite paragraph, insert:

```markdown
Bind the root working directory during construction or explicit initialization, before dataset registration or
partition preparation. The execution-entry operation does not select, reassign, or freshly prepare a working
directory. Opening an existing persisted execution is also distinct from fresh initialization: it validates and opens
the existing managed layout without clearing, replacing, or repairing it implicitly.
```

Under `#### Copying, reuse, and recovery`, replace the paragraph beginning:

> Unchanged model evaluation configuration has resume semantics...

with:

```markdown
Unchanged model evaluation configuration has resume semantics, including after worker changes, explicit root
interruption, or unexpected root-process termination. These cases use one persisted-state reconciliation procedure:
open the existing managed directory without fresh initialization, load the committed parent configuration and durable
execution state, load the referenced authoritative partition, verify complete persisted attempt results, reconcile
applicable worker observations, and dispatch only unfinished eligible work.

After explicit interruption, the existing in-memory computation instance may invoke that procedure. After unexpected
root-process termination, the user recreates the root-side computation instance against the existing working directory
and the same procedure reconstructs it from durable state. Do not create separate persistence schemas or competing
resume algorithms for those entry paths.

The trigger remains observable. Explicit interruption records the applicable interrupted/stop dispositions and permits
prospective configuration edits under the established rules. Unexpected process termination cannot retroactively
record an interruption event that did not occur; recovery begins from the last successfully persisted observations.
Both paths preserve the same parent identity, scientific configuration, partition association, accepted results,
selection evidence, and remaining retry budgets.

Fresh initialization for changed model evaluation configuration prepares a fresh-execution filesystem boundary; it is
not resume or recovery. Exact public constructor, execution-entry, and reconstruction signatures remain deferred.
Copies referring to the same persisted execution remain subject to the same coordinator ownership, task identity, and
at-most-one acceptance invariants; copying does not authorize uncoordinated controllers of the same state.
```

# MY ADVICE: propose removal of exact method name specification in `AGENTS.md` and allow later planning of method names first. The later planning step can use any method name for this functionality. Do not fix the name in `AGENTS.md`, which is too detailed for `AGENTS.md` instructions.
